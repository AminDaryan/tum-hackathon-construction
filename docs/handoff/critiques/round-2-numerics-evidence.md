# Critique: numerics-evidence

**Status:** Applied during Phase 1 (exact decimal bounds, tolerances, evidence model). Deferred items are listed in docs/handoff/NEXT_STEPS.md.

## Overall

Several basics are already right: Decimal values serialize as strings, arithmetic runs in a 60-digit context that traps errors, ParseStatus is categorical, the accessors abstain, and only reviewers can set human_confirmed_error. But the evidence semantics are advisory rather than enforced: nothing ties evidence class to detector category, the downgrade looks only at highlighted cells and treats unknown confidence as verified, and model_copy bypasses every validator. On the numerical side, four gaps need fixing in the models and contracts before eight people build on them, because each will give wrong or hidden results as soon as the planned detectors land: the undefined float-to-Decimal rule at ingestion, the Decimal-to-float coercion in evidence data, the missing section hierarchy for subtotal scope, and a subtotal tolerance that grows with the number of items.

## 1. [high] backend/app/validation/contracts/detector.py::DetectorSpec; backend/app/validation/contracts/issue_factory.py::IssueFactory.create; backend/app/models/base.py::FrozenModel (model_copy guidance); backend/app/validation/pipeline.py::ValidationPipeline._run_step; backend/app/models/issue.py::AnomalyScore

**Problem:** No code enforces the evidence-class rules. (a) DetectorSpec accepts category=STATISTICAL with evidence_classes=(confirmed_rule_violation,), and IssueFactory.create never checks evidence_class against spec.evidence_classes or spec.category. I confirmed this by running it: a 'statistical.mad' detector created a confirmed_rule_violation that carried AnomalyScore(value=0.97, interpretation='probability of error', calibrated=True). (b) AnomalyScore.calibrated is a plain bool the detector sets itself, with no reference to a calibration or evaluation. Any detector can turn a raw score into a 'probability'. (c) The FrozenModel docstring tells everyone to change records with model_copy(update=...), and that skips every validator. I confirmed four bypasses: an issue the factory had downgraded was set back to confirmed_rule_violation; evidence_class=human_confirmed_error was accepted; review_status jumped from pending_review to corrected (that status should only come from the correction workflow) with a 100,000-character reviewer_comment (the limit is 4000); FinancialImpact.amount became the float 0.30000000000000004 with currency '$'. The test suite itself models review decisions this way, so the review service will copy the pattern. (d) The pipeline only checks detector_id and run_id. Issues that were built directly or edited afterwards are stored as they are.

**Fix:** Add a DetectorSpec model_validator that maps each category to its allowed evidence classes. statistical/machine_learning/research: suspected_anomaly, extraction_uncertainty, needs_external_context. semantic: semantic_warning, needs_external_context. Only deterministic and domain detectors may declare confirmed_rule_violation. In IssueFactory.create, reject an evidence_class not in spec.evidence_classes, a category not in spec.issue_categories, and an anomaly_score on any class other than suspected_anomaly. Make AnomalyScore(calibrated=True) require a calibration_reference (an evaluation report id) that the spec declares. Replace the model_copy guidance with a validating FrozenModel.evolve(**changes), implemented as model_validate({**self.model_dump(), **changes}), and use it for review decisions. In _run_step, re-validate every returned issue and apply the evidence policy again through one function that both create() and the pipeline call (for example factory.enforce(issue)).

## 2. [high] backend/app/validation/contracts/issue_factory.py::IssueFactory.create (downgrade block); backend/app/validation/pipeline.py::ValidationPipeline.execute/_dataset_warnings

**Problem:** The rule 'confirmed only on verified input data' is checked only over `cells`, the affected (highlighted) cells. Reconciliation detectors will naturally highlight the total and list the summands or factors in EvidenceItem.cells, and the factory ignores those. I confirmed that a subtotal mismatch with a summand OCR'd at confidence 0.30 stays confirmed_rule_violation with extraction_confidence 1.0. A line-total issue that highlights only the line_total cell also escapes when qty or price was misread. An issue with no cells (a table-level 'grand total mismatch') is always confirmed. Dataset-level quality is ignored: execute() runs and keeps confirmed issues even when dataset.extraction.quality is FAILED (confirmed; the warning text even says 'needs review'). NEEDS_REVIEW warnings carry table_id and source but never change the issues they affect.

**Fix:** Add a required, non-empty `inputs: Sequence[CellRef]` to create() for confirmed_rule_violation. Apply the policy over affected cells ∪ inputs ∪ every EvidenceItem.cells, and resolve and integrity-check those refs too. Refuse to execute on ExtractionQuality.FAILED. For NEEDS_REVIEW, downgrade (or at least annotate) confirmed issues whose inputs fall in a table or location covered by an ExtractionWarning that affects values or structure. Give FAILED its own warning text.

## 3. [high] backend/app/models/dataset.py::Row.section_row_id / RowClassification / RowKind; backend/app/validation/contracts/context.py::ValidationContext.rows; backend/app/profiles/boq.yaml row_classification.grand_total_patterns

**Problem:** The canonical model cannot express what a subtotal or grand total covers, so the planned subtotal and grand-total detectors will raise false confirmed violations. (a) section_row_id is only the 'nearest preceding SECTION row', and SECTION rows record no parent, even though boq.yaml's section_code_pattern explicitly allows two levels ('01', '01.02'). Take 'Titel 01 > 01.01, 01.02; Summe 01.01; Summe 01.02; Summe 01': the row 'Summe 01' gets section_row_id = 01.02, so it is compared with 01.02's items only, or with zero items if scope means 'rows since the previous subtotal'. Summing SUBTOTAL rows for the grand total double-counts nested subtotals. (b) There is no way to mark items that are listed but not counted in totals (German Wahl-/Bedarfspositionen 'nur EP', alternates), so every section that contains one fails to reconcile. (c) The bare pattern '^\s*total\s*:?\s*$' classifies every per-section 'Total' line in English BoQs as GRAND_TOTAL (while a bare 'Summe' becomes a subtotal). The result is several grand totals per table, each compared with all items. (d) context.rows() silently drops rows a reviewer excluded, so a section that contains an excluded item stops adding up. The number accessors also return None for ambiguous or error summands, which makes 'sum the rest' the easiest path. (e) Nothing says whether sums use reported or recomputed line totals. If recomputed, one wrong line is reported twice (line_total and subtotal), with its financial impact counted twice.

**Fix:** Add the hierarchy to the model now, because normalization is being written against it. Add parent_section_row_id and section_level on SECTION rows (or a Row.section_path). Add RowClassification.closes_section_row_id on SUBTOTAL rows; when normalization cannot resolve it, leave it None and have the detector abstain. Add Row.counts_toward_totals, set from profile patterns for optional and alternative items. Remove the bare 'Total' grand-total pattern (treat it as a subtotal unless it is the last total row). Write the reconciliation contract into decimal_math or context. A subtotal is the sum of reported line_total values of counted ITEM rows in the section subtree (or the sum of its child subtotals). A grand total is the sum of counted ITEM rows of the table, independent of subtotals. If any summand is unusable, any row in scope is excluded, or explicit currencies conflict, abstain (count it in coverage and use needs_external_context or extraction_uncertainty); never sum the remainder. Provide a context helper that returns the scope with excluded rows included.

## 4. [high] backend/app/ingestion/base.py::RawCell.number; backend/app/models/values.py::NumberValue.value (also issue.py::FinancialImpact.amount, decimal_math.TolerancePolicy, profile.FieldConstraints); backend/app/repositories/base.py

**Problem:** openpyxl 3.1.5 returns Python floats (_cast_number calls float(...)), and the contract only says 'exact Decimal (never a float)'. Decimal(f) is the 'exact' conversion and gives Decimal('0.1000000000000000055511151231257827021181583404541015625'). Even Decimal(repr(f)) keeps the binary noise that Excel stores in cached formula results: =1.1*3 is cached as 3.3000000000000003. Consequences: max_decimal_places and integer_only constraints flag computed cells as confirmed violations; exact-duplicate detection misses 3.3 vs 3.3000000000000003; HALF_UP rounding of Decimal(2.675) gives 2.67 where Excel's ROUND gives 2.68; observed values show 17-plus digits of noise. The models also accept floats in lax mode: NumberValue(value=1.1*3) gives Decimal('3.3000000000000003'), and JSON numbers are accepted. Float noise from openpyxl, from the JavaScript frontend (corrections) or from an LLM plan therefore enters money fields without any error. The repository contract is silent on numeric storage, and SQLAlchemy Numeric on SQLite stores REAL.

**Fix:** Specify in RawCell: ints stay ints (check bool first); floats become Decimal(format(f, '.15g')), which is Excel's 15-significant-digit precision and also strips the noise in cached results; never Decimal(f); keep the repr in raw_value for audit. Introduce an ExactDecimal annotated type (a BeforeValidator that rejects float, so JSON input must be a string) and use it for NumberValue.value, FinancialImpact.amount, FieldConstraints and TolerancePolicy. State in repositories/base.py that Decimals are persisted as TEXT (JSON strings), never as Numeric or REAL.

## 5. [high] backend/app/models/issue.py::EvidenceItem.data (JsonScalar), FinancialImpact; backend/app/validation/contracts/issue_factory.py::IssueFactory.create

**Problem:** Confirmed: EvidenceItem(data={'diff': Decimal('0.10'), 'whole': Decimal('5.00'), 'big': Decimal('12345678901234567890.12')}) silently stores the floats 0.1, 5.0 and 1.2345678901234567e+19. The 'decimals as strings' comment is not enforced. Every reconciliation detector that records operands or differences will therefore write floats into persisted evidence and into the JSON, PDF and XLSX exports (scale is lost, and exact products longer than 15 digits are altered). That contradicts the brief's rule that money is never floating point. Beyond that bug, the model has no typed way to express a calculation (operands with their cells, the operation, exact vs rounded result, rounding spec, tolerance, allowed difference, number of terms). The line_total, subtotal and grand_total authors and three exporters will each invent their own keys. FinancialImpact records a signed 'impact' = reported − recomputed, but a line-total mismatch cannot tell which of qty, price or total is wrong. Example: a price typed as 125.0 instead of 12.50 next to a correct total produces an 'impact' of −4,500 on a total that is right. FinancialImpact also has no reported or recomputed fields, stays displayed on downgraded issues, and has nothing that stops a summary from adding the line and subtotal discrepancies together. EvidenceItem.cells and caller-supplied CellRef.source are never resolved or checked, so evidence navigation can point at cells that do not exist or at the wrong A1 address.

**Fix:** Make EvidenceItem.data reject float and Decimal (or convert Decimal with format(d, 'f') in a before-validator). Add a typed CalculationEvidence {operands: [{label, cell, value: Decimal}], operation, exact_result, rounding: RoundingSpec|None, rounded_result, reported, difference, allowed_difference, terms} that the UI and the exporters render. Extend FinancialImpact with reported, recomputed, a kind ('discrepancy' when the wrong operand is unknown) and an overlap/aggregation key. Drop or flag the impact when the issue is downgraded. Resolve EvidenceItem.cells in the factory and overwrite CellRef.source with the resolved cell's source.

## 6. [high] backend/app/models/dataset.py::Cell.extraction_confidence; backend/app/models/issue.py::ValidationIssue.extraction_confidence; backend/app/validation/contracts/context.py::USABLE_PARSE_STATUSES; backend/app/core/config.py::ValidationLimits.low_confidence_threshold

**Problem:** One float carries meanings that do not fit together. The Cell comment requires 1.0 for digital sources, and the factory copies the minimum into ValidationIssue.extraction_confidence. Every XLSX and CSV finding will therefore display 'extraction confidence 1.0', an invented number the brief forbids (Part J, and Part B's 'never claim 100%'). None means unknown (an OCR adapter without per-cell scores, cells rebuilt from several words, digital PDFs whose text is verbatim but whose column assignment is guessed), yet None is treated as verified. PDF and OCR findings caused by misaligned columns will therefore be confirmed. OCR engine scores are uncalibrated and differ by engine (Tesseract word confidence 0–100, PaddleOCR line scores), yet they are compared with one global 0.9 threshold and shown as bare floats. Parse status is ignored: INFERRED values (decimal separator guessed from column evidence) count as verified, so one wrong column-level guess makes every row a confirmed mismatch. user_edited is ignored, so an OCR cell a reviewer has corrected stays 'low confidence' forever.

**Fix:** Use None for digital sources, and replace the float with a provenance record, for example ExtractionReliability{method: typed_cell|delimited_text|pdf_text_layout|ocr|user_verified, engine, engine_version, score: float|None, score_calibrated: False, structure: exact|reconstructed}. Put a single verified(cell) predicate in the factory: typed, delimited and user_verified cells with parse_status EXACT are verified; INFERRED values get an annotation (or count as verified only when the column-level guess was unanimous); OCR cells are verified only at or above a per-adapter threshold; unknown or reconstructed cells are unverified. Show engine scores only for OCR inputs, labelled with the engine, and never as a percentage.

## 7. [medium] backend/app/validation/contracts/issue_factory.py::IssueFactory._fingerprint / create; backend/app/validation/pipeline.py::ValidationPipeline.execute (fingerprint dedupe)

**Problem:** The fingerprint is detector|category|table|row|cells|optional key, so two different rules on the same cell collide. I confirmed that a field-constraints detector reporting both 'Below minimum' and 'More than 2 decimal places' on one unit_price cell ends up with one stored issue. The other is dropped with the note '1 duplicate finding(s) merged', and the report still says issues_found=2. The fingerprint also changes depending on whether the optional `row` argument was passed (row_id None vs set), so a refactor breaks review matching. It contains no evidence, so carrying a review forward 'by fingerprint' (its documented purpose) would apply a 'false positive' made on revision 1 (difference 0.40) to revision 2, where the same cell now differs by 4,000. It is also built from random ids that build_dataset regenerates on every normalization (for example after the reviewer picks a different header row), which orphans every review decision.

**Fix:** Replace fingerprint_key with a required rule_id, store it on the issue and include it in the hash. Derive row_id and table_id from the cells when they share a row, and validate that table, row and cells are consistent. Add evidence_digest = hash(observed, expected, input values), and carry a review forward only when both fingerprint and digest match (otherwise mark it 'previously reviewed, evidence changed'). Deduplicate only when fingerprint and digest are both identical, and count issues_found after merging. Define id stability: corrections copy ids; re-normalization reuses ids keyed by document sha + sheet index + source row/column.

## 8. [medium] backend/app/validation/contracts/decimal_math.py::TolerancePolicy; backend/app/profiles/boq.yaml detector_defaults deterministic.subtotal / deterministic.grand_total

**Problem:** per_term_absolute 0.005 makes the allowance grow linearly. Confirmed: allowed_difference is 0.26 for 50 terms, 1.01 for 200, 5.01 for 1,000 and 10.01 for 2,000 (a grand total summed over all items). Summing reported line totals read from XLSX (full-precision cached values, or values that are already rounded) has zero rounding drift, so this tolerance only hides real discrepancies. A 1.00 mistake in a 200-item section passes silently as 'completed, 0 issues'. Drift exists only when the summands are display-rounded (CSV or PDF prints) and the printed total was computed from unrounded values, and even then its realistic size is about 0.003·√n, not 0.005·n. `terms` is undefined for grand totals (items or subtotals?). Separately, TolerancePolicy has no upper bounds (relative up to 1.0, absolute unbounded; I confirmed absolute=1E9 with relative=1 accepts 0 vs 123456). A plan can therefore configure reconciliation checks that can never fail while the run reports them as completed, including a future LLM plan steered by prompt injection in cell text.

**Fix:** Set per_term_absolute to 0 by default. Apply a drift allowance only when the summands are known to be display-rounded (from source kind or number_format scale). When |diff| is above `absolute` but inside the drift band, emit an info-level finding ('difference explainable by rounding') instead of passing silently. Define terms as the number of reported values summed. Cap TolerancePolicy (for example relative ≤ 0.01 and absolute ≤ a configured maximum). Have PlanValidator flag any tolerance wider than the profile default for human approval, and record it in DetectorRunReport.

## 9. [medium] backend/app/models/profile.py::UnitDefinition; backend/app/profiles/boq.yaml unit 'pct'; backend/app/models/values.py::value_to_display

**Problem:** BoQs routinely contain percentage items such as contingencies, preliminaries and surcharges: qty '5', unit '%', rate = base amount 100,000.00, amount 5,000.00. The profile maps '%' to unit pct (dimension ratio), but UnitDefinition has no quantity factor, and NumberValue.is_percent is set only when the quantity cell itself contains '%'. The line-total detector will compute 5 × 100,000 = 500,000 and raise a confirmed violation on a correct line. power_of_ten_factor returns -2 here (confirmed), so the explanation will add 'likely decimal-point error', which is the wrong mechanism. value_to_display also ignores is_percent, so reviewers see a '19 %' cell as observed value '0.19'.

**Fix:** Add UnitDefinition.quantity_factor (Decimal, default 1; pct and v.h. → 0.01; ‰ → 0.001), or a line_total_rule (multiply | percent_of_rate | not_applicable). line_total then computes qty × factor × price, unless the quantity already has is_percent, and abstains with needs_external_context for units whose convention the profile does not declare. Render is_percent values as percentages in value_to_display.

## 10. [medium] backend/app/profiles/currency.py::DEFAULT_CURRENCY_ALIASES, _EXCEL_CURRENCY_TAG, CurrencyResolver.find_in_number_format / find_in_text

**Problem:** The module promises that only explicit markers count as evidence, but it maps ambiguous symbols to a single ISO code and throws away the Excel locale id that would decide them. Confirmed: '[$$-C09]#,##0.00' (Australian dollar) → USD; '[$$-1009]' (Canadian dollar) → USD; '[$¥-804]' (Chinese yuan) → JPY; '"$"…' → USD; find_in_text('CAD drawing ref') → {'CAD'}; 'fr.' → CHF. openpyxl renders the implicit built-in formats 5–8, 42 and 44 as US '"$"' codes regardless of the workbook's locale, and those also resolve to USD (confirmed for 44). BoQs are common in AUD, NZD, SGD, HKD and CAD markets. A header 'Rate (AUD)' plus cells formatted [$$-C09] produces a confirmed 'mixed currencies USD/AUD' violation on a consistent document, and FinancialImpact.currency shows the wrong currency.

**Fix:** Resolve ISO codes and unambiguous names directly. For '$', '¥', 'kr' and 'fr.', return a set of candidate codes, and treat built-in '"$"' formats as 'currency symbol, code unknown'. Parse the LCID in [$symbol-LCID] with a small table (409→USD, C09→AUD, 1009→CAD, 1409→NZD, 804→CNY, 411→JPY, …). Make the currency detector treat a candidate set as compatible with any of its members, and leave FinancialImpact.currency as None when the currency is ambiguous. Match currency words only in headers of monetary columns, or in tokens that are bracketed or next to a number.

## 11. [medium] backend/app/profiles/boq.yaml detector_defaults deterministic.unit_compatibility.description_rules

**Problem:** These rules guess what an item is from a regex on its description and then assert which unit dimensions are allowed. They are configured for a detector in the deterministic category, whose natural evidence class is confirmed_rule_violation, and the rule schema has no evidence class of its own. A match on description text is text analysis: the brief calls that a 'semantic warning' and allows contextual unit rules only 'when the category is sufficiently established'. Example: 'Baustelleneinrichtung: Bauzaun stellen und vorhalten, 120 m' is a legitimate per-metre position, and the site_setup rule would turn it into a confirmed unit violation.

**Fix:** Give the rule schema that the unit_compatibility config model will define an evidence_class field, defaulting to semantic_warning, and disallow confirmed_rule_violation for text-pattern rules. Alternatively, move description rules to a domain or semantic detector. Keep confirmed violations for facts about the vocabulary or dimensions (an unknown unit, conflicting dimensions between columns).

## 12. [low] backend/app/validation/contracts/decimal_math.py::RoundingSpec / TolerancePolicy.within; backend/app/profiles/boq.yaml deterministic.line_total

**Problem:** The contract does not say which side of the comparison is rounded, or to what precision. decimal_places is fixed at 2, so a document that rounds amounts to whole units (JPY, or whole-euro cost estimates) gets a confirmed violation on every line whose product has a fraction: 0.75 × 1,234 = 925.50 vs a reported 926 is a difference of 0.50, above the 0.01 tolerance. A reported value that is an unrounded formula result (4.9995, displayed as 5.00) passes only because of the ±0.01 slack. Set absolute to 0 ('strict') and an exactly correct line fails against the rounded recomputation.

**Fix:** Specify that a line passes if the reported value is within tolerance of either the exact product or the product rounded to the document's precision. When the profile does not pin that precision, infer it from the line_total column's number_format, from the largest scale among reported values, or from the ISO 4217 minor units of a resolved currency. Record in the calculation evidence which convention matched. Abstain, or emit an info finding, when the column's precision is inconsistent.

## 13. [low] backend/app/validation/contracts/decimal_math.py::power_of_ten_factor

**Problem:** The scaled comparison reuses the reconciliation tolerance. Its absolute floor does not scale with 10^k, and its relative band is wide when you think in ratios. Confirmed: observed 0.01 vs expected 500 → k=-5 (500·10^-5 = 0.005); 0.009 vs 3 → k=-3; 0.01 vs 0.5 → k=-2. With relative 5 %, 1040 vs 105 (ratio 9.9) → k=1. Each of these would add a specific 'decimal-point error' mechanism to a confirmed issue's explanation that the numbers do not support.

**Fix:** Compare ratios instead. Require |observed| to be at least 100 times the rounding quantum (3 or more significant digits), and require RoundingSpec.apply(expected × 10^k) == observed, or |observed / (expected·10^k) − 1| ≤ 0.5 %. Never use the reconciliation tolerance's absolute or relative terms for scaled matches. Pass the exact (unrounded) product as expected.

## 14. [low] backend/app/models/values.py::NumberValue / value_to_display; backend/app/validation/contracts/decimal_math.py::RoundingSpec.apply / multiply

**Problem:** NumberValue accepts any finite Decimal. Confirmed: value_to_display(NumberValue(value=Decimal('1E+999999'))) builds a 1,000,000-character string. If the parser accepts exponents (as Decimal() does), a hostile CSV of such cells blows up issue text, grids and exports. RoundingSpec.apply(Decimal('1E+60')) raises InvalidOperation in the 60-digit context, so a single such cell makes the whole line_total detector FAIL and throws away all of its findings for the dataset (Overflow from multiply does the same).

**Fix:** Bound NumberValue (for example ≤ 34 significant digits and an adjusted exponent within ±30) so that normalization marks out-of-range values FAILED with a warning. Have decimal_math raise a typed per-row abstention (or return None) that detectors count in coverage, instead of letting InvalidOperation or Overflow abort the detector.
