# Critique: maintainability

**Status:** NOT triaged yet: it finished after the handoff snapshot. Triage it first (NEXT_STEPS.md, step 1).

## Overall

Layering and dependency-injection seams are sound: models import only core, normalization depends only on ingestion, models and core, and ids, clock and settings are injected. The contracts that bind the eight implementers are not pinned down yet: profile config shapes, issue identity, normalization output, total scopes, review concurrency and versioning, and dataset revisions still exist only in docstrings or in test-builder behaviour, so parallel work will diverge on them. The tree was still being edited during the review (last change around 21:29; the suite is now 511 passed, 1 failed in test_xlsx_adapter), so fix the high items, commit a green, locked baseline, and only then branch.

## 1. [high] backend/app/profiles/boq.yaml detector_defaults; app/models/profile.py DomainProfile.detector_defaults; app/validation/plan_validation.py PlanValidator.validate

**Problem:** boq.yaml already fixes config shapes for six detectors that do not exist yet (app/validation/deterministic/ holds only _support.py): rounding/tolerance, only_populated_columns/exemptions, text_references[{rule_id,text_field,pattern,target_field}], description_rules[{...,exclude_pattern,allowed_dimensions,rationale}]. No code defines these shapes, and DomainProfile checks only the id pattern. PlanValidator merges profile defaults into every step and raises a single PlanValidationError for the whole plan if any step fails. Verified: a unit_compatibility detector whose config model names its list `rules` makes the BASELINE plan fail with invalid_validation_plan, so no checks run on any BoQ document. That contradicts the brief's rule (Part F) that the baseline must never block basic functionality. A mistyped key such as `deterministic.line_totals` is accepted silently, so that detector runs with its code defaults (a different tolerance) and nobody notices. Three detector-group implementers will each invent their config models against this YAML.

**Fix:** Before branching, define the config models in code, for example validation/contracts/configs.py with ReconciliationConfig{rounding: RoundingSpec, tolerance: TolerancePolicy}, RequiredValuesConfig{only_populated_columns, exemptions}, TextReferenceRule and DescriptionUnitRule, and have the detectors use them. Add validate_profiles(catalog, registry), run at startup and in a unit test: it resolves every detector_defaults entry through registry.resolve_config and rejects unknown ids in detector_defaults and disabled_detectors. In the baseline path, turn a step whose profile config fails into a FAILED DetectorRunReport for that step and keep running the others, instead of rejecting the whole plan.

## 2. [high] app/validation/contracts/issue_factory.py IssueFactory._fingerprint/_digest and create(fingerprint_key=...); app/validation/pipeline.py ValidationPipeline.execute (dedup on (fingerprint, evidence_digest))

**Problem:** The fingerprint covers detector, category, rule, table, row, the anchor cell coordinates and an optional fingerprint_key. The digest covers observed, expected and cell values. Title, explanation, inputs and evidence are in neither. Findings at table level or without anchors, and several findings of one rule on the same cell, therefore collide unless the detector passes fingerprint_key, which the create() docstring never mentions. Verified: four 'required field not mapped' findings for different fields became 1 stored issue plus the note '3 duplicate finding(s) merged'. data-model.md and ValidationIssue make (fingerprint, digest) the key that carries review decisions into later runs. Marking one such finding a false positive would therefore also suppress the others in the next run.

**Fix:** Rename fingerprint_key to a documented, keyword-only `subject` (field id, referenced code or rule target). Require it when `cells` is empty and include it in the digest. Have IssueFactory.create raise IssuePolicyError when a run produces a duplicate fingerprint, so detector unit tests fail fast. The pipeline should then merge only fully identical issues and report any other collision as a detector defect, not as a note.

## 3. [high] app/normalization/builder.py build_dataset contract; docs/architecture/data-model.md; app/models/dataset.py Cell.normalized_value; tests/support/builders.py (_cell, text_cell, unit cells, empty_cell); app/validation/contracts/context.py; app/models/schema.py TableDecisions.unit_aliases; app/ingestion/csv_adapter.py and xlsx_adapter.py

**Problem:** Detector authors will write and test against builders that assume: text normalized_value == ' '.join(text.split()); a unit cell's normalized_value == the UnitCatalog unit_id; a whitespace-only cell becomes EMPTY; a failed number becomes TEXT/FAILED. None of this is in the normalization contract or in data-model.md, and the real adapters already contradict the whitespace assumption: CSV (`if value:`) and XLSX (`value != ""`) both emit whitespace-only text as STRING cells. Suppose normalization keeps those cells as TEXT, applies NFKC or casefolding, or stores the raw unit alias. Then detectors that pass every unit test misfire on real files: required-value checks miss blank cells, unit_compatibility compares aliases, and reference matching fails. ValidationContext has no unit accessor, so detectors cannot see the reviewer's unit_aliases decisions in TableDecisions. Hidden sheets are dropped ('non-empty, non-hidden'), although hidden rows are deliberately kept because they may belong to a total.

**Fix:** Write the output matrix into builder.py and data-model.md now: raw type x parse outcome -> data_type, parse_status, normalized_value, marker, plus the exact text and unit normalization rules. Implement it once as shared helpers (normalize_text, is_blank, make_cell) in app/models or app/core, used by both normalization and tests/support/builders. Add ValidationContext.unit(table, row), which returns the canonical unit after decisions are applied. Decide hidden sheets explicitly, for example normalize them and attach a warning, as is already done for hidden rows.

## 4. [high] app/repositories/sql/unit_of_work.py _begin (connection.begin()) and sql/database.py _create_engine; app/repositories/base.py IssueRepository.update / AuditRepository; app/models/issue.py ValidationIssue (no version); docs/api/rest-api.md POST /issues/{id}/review; frontend/src/services/issuesService.js submitReview

**Problem:** The in-memory UoW and the SQL adapter's in-memory mode (Database.in_memory_sqlite, which every [sqlite] repository test uses) serialize all units of work behind an ExclusiveLock. A file database does not. There, pysqlite's legacy transaction control sends BEGIN only at the first INSERT/UPDATE/DELETE. Verified with the same engine options: after a SELECT inside connection.begin(), in_transaction is False. So in production the review read-check-write is not atomic: issues.get, then check_review_transition, then issues.update (a blind UPDATE by id), then audit.append. Take two near-simultaneous review requests (two tabs, a double click, FastAPI's threadpool). Both read 'open', and the second overwrites the first. Its transition was checked against a status that no longer applies, and its audit event records before='open' although the stored status was the first decision. The decision is lost and the audit chain is broken, which matters because the brief (Part H) requires an audit history of reviewer decisions. Separately, overview.md promises 'versioned updates', but ValidationIssue has no version, the API takes only {status, comment}, and the frontend already sends exactly that, so a decision made on a stale screen cannot be detected.

**Fix:** In the SQL adapter, open the SQLite transaction explicitly: set the driver to autocommit mode (isolation_level=None) and run BEGIN, or BEGIN IMMEDIATE for writing units of work, in a 'begin' event listener, as the SQLAlchemy SQLite docs recommend. Add a two-thread test on a file database. Add `version: int` to ValidationIssue and change the protocol to update(issue, *, expected_version), implemented as UPDATE ... WHERE issue_id=? AND version=?, which raises ConflictError (mapped to 409 by the API). Carry the version in the review request body or an If-Match header, and update issuesService.submitReview now. Put the transition and audit-event construction in one model or service method that every caller uses, and make AuditEvent.entity_type an enum.

## 5. [medium] app/models/dataset.py RowClassification.counts_toward_totals / not_counted_above_section_id, Row.closes_section_id / source_hidden / outline_level / belongs_to_row_id, SCOPE_BOUNDARY_KINDS; nothing in app/validation/contracts

**Problem:** Which rows a total sums over depends on about eight interacting fields, and their rules exist only in docstrings. counts_toward_totals=None means 'evaluate both readings and abstain if they disagree'. A hidden row is an 'alternative reading'. ADJUSTMENT, CARRY_FORWARD and SUMMARY_LINE rows get special treatment. The subtotal and grand-total detectors, which may belong to different implementers, will each work out member rows on their own. On the same workbook one can confirm a mismatch the other passes, or the grand total can count subtotals twice. Contradictory 'confirmed' findings are the most damaging output an integrity tool can give.

**Fix:** Add app/validation/contracts/scopes.py with subtotal_scope(context, table, total_row) and grand_total_scope(context, table, total_row). Each returns the member rows for every reading plus abstain reasons, and is unit-tested on nested sections, carry-forward, hidden rows, not-counted items and closes_section by code. Make both detectors and the summary-line check use it, and write that rule into the detector contract.

## 6. [medium] app/validation/deterministic/_support.py normalize_code, code_segments, is_strict_prefix; docs/architecture/overview.md layer rules

**Problem:** Normalization needs the same code canonicalization: RowClassificationRules step 6 ('code is a strict prefix of the next item's code'), section levels, closes_section by code, and decisions keyed by codes. The layer rules forbid normalization from importing app.validation, so the normalization implementer will reimplement it. The two copies will drift on leading zeros, trailing dots, slashes and NFKC. The section that normalization assigns will then disagree with the reference or subtotal scope the detectors compute, for codes such as '01.02.0030.' vs '1.2.30'.

**Fix:** Move normalize_code, code_segments, is_strict_prefix and MAX_CODE_SEGMENT_CHARS to a layer both can import, such as app/core/codes.py or app/profiles/codes.py. Re-export them from _support and add a test that pins the canonical form.

## 7. [medium] docs/architecture/validation-engine.md (linked from overview.md but missing; docs/decisions and docs/algorithms are empty); app/validation/contracts

**Problem:** Nothing says which detector reports which cell condition: #REF!/ERROR, an UNAVAILABLE cached formula, an AMBIGUOUS or FAILED parse, a MARKER, a missing unit. A single #REF! in a line_total cell will be reported by line_total, subtotal, grand_total and required_values. Fingerprints include detector_id, so the pipeline never merges these findings. Counts are inflated and reviewers dismiss the same cell four times. Coverage keys are free-form strings, so the detector catalogue (brief Part M) and the frontend cannot sum or compare coverage.

**Fix:** Write validation-engine.md before branching. It needs an ownership table (condition -> owning detector, and what the other detectors do, e.g. abstain and count it under a standard coverage key such as skipped_unparseable), the coverage-key vocabulary, and the rule that arithmetic detectors abstain on inputs that are not EXACT, except INFERRED inputs, which they use with a caveat. Back it with one shared cell_condition(cell) classifier in validation/contracts.

## 8. [medium] app/normalization/builder.py build_dataset (no dataset_id/revision parameters); app/repositories/base.py DatasetRepository (add, get, list_for_document); app/models/dataset.py Cell docstring ('explicit overlay') and validation/contracts/context.py, versus docs/architecture/data-model.md and the brief (corrections -> revision N+1)

**Problem:** Reviewer corrections are described two incompatible ways. Cell and ValidationContext call them an overlay, while the brief and data-model.md say corrections create dataset revision N+1. IssueFactory's digest and every context accessor read cell.normalized_value directly, so an overlay would have to touch every detector and the factory. build_dataset mints its own ids and cannot produce revision N+1 of an existing dataset. DatasetRepository has no latest_for_document and no guard against a stale parent revision, and list_for_document returns full datasets. The persistence, API and frontend implementers will each pick a different model.

**Fix:** Decide and document the model now. Recommended: corrections are materialized as revision N+1 with the same dataset_id, row ids and cell ids, and the diff goes into the audit trail; re-normalization creates a new dataset_id, with decisions keyed by source coordinates. Let build_dataset accept dataset_id and revision, or add a separate revise(dataset, corrections) function. Add add_revision(dataset, *, expected_parent_revision) and a lightweight latest/headers query to DatasetRepository, and remove the overlay wording.

## 9. [medium] backend/pyproject.toml [project.dependencies] (lower bounds only, no lock file) and [tool.pytest.ini_options] filterwarnings = error::DeprecationWarning:app.*; no CI configuration in the repository

**Problem:** A fresh install today resolved SQLAlchemy 2.1.9 and pydantic 2.14.3, and 26 tests failed during this review with no code change behind them. 24 failed because SQLAlchemy 2.1 deprecates Result.tuples() and app warnings are errors. 2 failed because pydantic 2.14's model_dump(mode='json') silently turns NaN into null, which disabled the repository's strict-JSON guard. The persistence implementer has since patched both locally. With eight people installing on different days and no CI, every machine gets a different red/green baseline, so regressions cannot be told apart from drift and fixes will conflict. The frontend has package-lock.json; the backend has nothing equivalent.

**Fix:** Commit a backend lock file (uv.lock or a pip-compile constraints file) that pins exact versions, and use it in every setup and in CI. Add one CI job (backend pytest and ruff, frontend tests) that every branch must pass before merging.

## 10. [low] app/validation/deterministic/_support.py explicit_currency; app/profiles/currency.py CurrencyResolver; app/models/issue.py FinancialImpact.currency

**Problem:** explicit_currency uses only header_currency and NumberValue.currency and ignores a FieldRole.CURRENCY column, which CurrencyResolver's docstring lists as explicit evidence. Take a BoQ with a currency column holding EUR: detectors that use _support attach no currency, while any that use the resolver attach EUR. FinancialImpact.currency is optional, although data-model.md says an impact exists only with an explicit currency, so impacts without a currency can be summed across currencies in the API or frontend.

**Fix:** Add a single ValidationContext.currency_evidence(table, row, field_ids) built on CurrencyResolver and delete explicit_currency. Make FinancialImpact.currency required, and leave the impact out when no explicit currency exists.

## 11. [low] backend/tests/support/builders.py make_context and DatasetBuilder; app/validation/pipeline.py ValidationPipeline.execute (context and factory wiring)

**Problem:** make_context builds its own ValidationContext and IssueFactory without review_tables, caps or a Deadline. A detector that swallows DetectorStopped or IssueLimitReached, or never calls context.checkpoint(), passes every unit test but breaks the time limit and issue cap in the real pipeline. Its findings on review tables also lack the caveat the pipeline adds. DatasetBuilder(quality=...) sets the quality without creating the warnings that justify it, and SUBTOTAL rows default to closes_section=False, which may not match what normalization emits.

**Fix:** Extract one build_validation_context(dataset, profile, run_id, limits, ids, clock) factory from the pipeline and have make_context call it, with small default limits so the caps are exercised in tests. Derive quality from warnings in the builder, and make its row-kind defaults match the documented normalization output.

## 12. [low] app/core/config.py IngestionLimits.header_scan_rows; app/normalization/builder.py NormalizationOptions(header_scan_rows=30, type_dominance_threshold=0.8, max_label_chars=500); app/core/patterns.py MAX_MATCH_CHARS=500

**Problem:** Several knobs live in two places, against the brief's centralized-config rule (Part B). Raising NormalizationOptions.max_label_chars has no effect, because profile patterns still truncate at patterns.MAX_MATCH_CHARS. Changing IngestionLimits.header_scan_rows leaves normalization scanning 30 rows. type_dominance_threshold cannot be set through Settings at all.

**Fix:** Build NormalizationOptions from Settings (e.g. NormalizationOptions.from_settings), keep each limit in exactly one place, and have patterns read the same max-chars value.
