# Critique: adaptability

**Status:** Applied during Phase 1 (plannable parameters, section hierarchy, schema decisions, coordinate-based identity). Deferred items are listed in docs/handoff/NEXT_STEPS.md.

## Overall

The foundation is a good base, and most of its gaps can be closed with additive changes if they are fixed now. Its strengths are the immutable canonical model with provenance, the strict registry and config models, the single issue factory, exact Decimal math and profiles kept as data. But the contracts the parallel streams are about to build on assume a single header row, flat sections, grid-only extraction, fingerprints built from ids, single-pass runs and parameters that any plan may override. docs/architecture/overview.md promises 'no core changes' for PDF/OCR adapters, LLM planners, research detectors and new domains, and these contracts cannot deliver that. Exports (g) look fine once corrections and revisions are explicit; the seven high findings should be settled before normalization and the detectors are written.

## 1. [high] backend/app/validation/plan_validation.py :: PlanValidator.validate; backend/app/validation/registry/registry.py :: DetectorRegistry.resolve_config; backend/app/validation/contracts/detector.py :: DetectorConfig; docs/api/rest-api.md :: POST /datasets/{id}/validation-runs

**Problem:** Every parameter of every detector can be overridden by any plan. Plans come from clients (the REST doc says POST /validation-runs accepts {"plan": ValidationPlan}) and later from an LLM that reads untrusted cell text. Only types are checked. Verified: an LLM-kind plan setting deterministic.subtotal tolerance.absolute="1000000000" validates. A crafted or prompt-injected plan can therefore switch reconciliation off while the run reports zero violations; the only trace is a number in detector_reports[].config. boq.yaml already has regex-valued parameters: reference_integrity.text_references[].pattern and unit_compatibility.description_rules[].description_pattern. A plan can replace them wholesale with a catastrophic-backtracking pattern, and because runs are synchronous and Python re has no timeout, one request can freeze the backend. Three related defects sit in the same path. (a) resolve_config replaces only top-level keys. A partial override {"tolerance": {"absolute": "0.05"}} silently resets the profile's per_term_absolute from 0.005 to 0 (verified), which produces false subtotal violations on long sections. (b) PlanValidator ignores profile.disabled_detectors; only BaselinePlanner applies them. (c) ValidationPlan.planner is supplied by the client, so a hand-made plan can be recorded as "baseline".

**Fix:** Add a parameter policy to DetectorConfig before the 13 config models are written, e.g. ClassVar PLANNABLE: Mapping[str, bounds], or Field(json_schema_extra={"plannable": True, "max": ...}). Pass the planner kind into PlanValidator.validate: LLM plans, and USER plans unless an explicit advanced mode is on, may only set plannable keys, within bounds. Regex parameters stay profile-only, or are length-limited and run under a timeout or a linear-time engine. Deep-merge mapping layers: recurse into dicts, replace lists. Apply disabled_detectors in PlanValidator. Set plan.planner on the server from the code path that produced the plan.

## 2. [high] backend/app/models/dataset.py :: Row.section_row_id, RowClassification; backend/app/normalization/builder.py :: build_dataset contract ('assign section membership'); backend/app/profiles/boq.yaml :: row_classification.section_code_pattern

**Problem:** Section membership is a single pointer to the 'nearest preceding SECTION row'. Sections have no level or parent, and total rows have no scope; the test builder sets a section row's own section_row_id to None. Nested BoQs (Los > Titel > Untertitel, or '01' > '01.02', both levels accepted by boq.yaml's section_code_pattern) cannot be represented. Example: 01 / 01.01 with items 100 + 200 and 'Summe 01.01' = 300 / 01.02 with item 50 and 'Summe 01.02' = 50 / 'Summe 01' = 350. 'Summe 01' points at section 01.02, so a subtotal detector that sums its section's items gets 50 and raises a HIGH confirmed_rule_violation with a 300 financial impact. The subtotal, grand-total, section-consistency and grouping detectors would each have to re-infer the hierarchy. The 'identify section hierarchy' review step in Part I has no field to store the reviewer's decision.

**Fix:** Add hierarchy to the canonical row now. Give rows Row.section_path: tuple[str, ...] (ancestor SECTION row ids, outermost first) and give section classifications a level. Give SUBTOTAL, GRAND_TOTAL, TAX and GROSS_TOTAL rows Row.scope_row_id, the section the total closes (None means the whole table). Normalization derives levels from section codes and patterns and accepts reviewer overrides (see the schema-decisions finding). Provide one shared helper, e.g. ValidationContext.rows_in_scope(table, total_row), for every reconciliation detector to use.

## 3. [high] backend/app/normalization/builder.py :: build_dataset; backend/app/validation/contracts/issue_factory.py :: IssueFactory._fingerprint; backend/app/core/ids.py :: RandomIdFactory; backend/app/models/dataset.py :: HeaderDetection, ExtractionReport.quality; docs/architecture/data-model.md :: fingerprint

**Problem:** build_dataset(raw, profile, document_id, ids, clock, options) takes no reviewer decisions: header row, table region, manual column-to-field mapping, row-kind overrides, exclusions, hierarchy or unit confirmations. It also takes no previous revision to inherit identities from. Parse expectations (number vs text), unit normalization, header currency and row classification (label_fields, item_value_fields) all depend on the mapping. Every schema-review action therefore means re-normalizing, and RandomIdFactory mints new table, row and column ids each time. IssueFactory._fingerprint hashes those ids. Verified: the same detector on the same source cell A3, with different row ids, gives different fingerprints. This contradicts data-model.md ('hash of detector, category and location (not of ids or values)'); test_fingerprint_is_stable_across_runs_and_ids only varies run_id. After a header-row change, every review decision and correction reference is orphaned. Three more gaps: (a) HeaderDetection.header_row_number is a single int, so a two-row header such as 'Preis' over 'EP | GP' cannot be recorded or chosen. (b) RawWorkbook is transient, so the review UI has no rows above the detected header to pick from, and re-running OCR for every view is expensive. (c) ExtractionReport.quality is the only review state. A reviewed dataset stays needs_review, and every later run carries the 'findings may reflect extraction problems' warning unless the workflow rewrites extraction history.

**Fix:** Change the contract before normalization is implemented: build_dataset(raw, *, profile, decisions: SchemaDecisions | None = None, previous: Dataset | None = None, ...), with SchemaDecisions a persisted, versioned model. Make identity coordinate-based: derive table, column and row ids from (document_id, sheet/page/table index, source row/column), or carry them over from previous by source coordinates. Fingerprint on detector, category, SourceLocation coordinates and fingerprint_key, as the doc states. Replace header_row_number with header_row_numbers: list[int], plus per-column header parts. Persist the raw extraction, at least OCR output. Add a Dataset-level schema_review state (status, decided_by, decided_at) separate from ExtractionReport.quality, and base the pipeline warning on it.

## 4. [high] backend/app/models/dataset.py :: Cell.user_edited, Row.excluded; backend/app/validation/contracts/context.py :: ValidationContext.number_value, rows; backend/app/validation/contracts/issue_factory.py :: IssueFactory.create; backend/app/repositories/base.py :: UnitOfWork

**Problem:** The only way to record a correction is to overwrite the extracted fields and set user_edited, which no code reads. Every option gives wrong results. (a) If the corrected value goes into normalized_value and parse_status stays ambiguous or failed, number_value returns None and every detector ignores the human-supplied value. (b) If the OCR confidence (say 0.55) is kept, IssueFactory downgrades every finding on that human-verified cell to extraction_uncertainty forever. (c) If the workflow sets exact and 1.0, the cell falsely claims verbatim extraction, and the original provenance that exports and the audit trail must show (Part D 'user modifications', Part K) is lost. Row.excluded is a bare bool with two incompatible meanings. rows() drops excluded rows, so a reviewer who excludes a genuine item from checks (quantity 'see drawing') makes the subtotal detector leave out its amount and raise a false confirmed violation. A mis-parsed header or footer line, by contrast, really should be dropped. Proposed, applied and rejected corrections have no entity or repository, only audit events.

**Fix:** Add an explicit overlay: Cell.override: CellOverride | None (value: CellValue, correction_id, actor, at, reason). Leave raw/parsed/normalized values, parse_status and extraction_confidence untouched, and add an effective_value accessor. Context accessors read the override first, and IssueFactory treats overridden cells as verified. Replace Row.excluded with Row.exclusion: RowExclusion | None {scope: not_data | skip_checks, reason, actor, at}, and define how rows() and the aggregation helpers treat each scope. Add a Correction model and a CorrectionRepository on UnitOfWork (proposed/applied/rejected, issue_id, CellRef, before/after, resulting revision).

## 5. [high] backend/app/validation/contracts/issue_factory.py :: IssueFactory.create, IssueFactory._fingerprint

**Problem:** The downgrade policy ('a deterministic violation computed from low-confidence extracted cells is downgraded') looks only at `cells`, the affected cells that get highlighted. EvidenceItem.cells are not checked for existence and not considered for confidence. Reconciliation detectors naturally anchor on the total cell and cite the summands as evidence. Verified: a subtotal issue whose summand has OCR confidence 0.40 stays confirmed_rule_violation, and a dangling evidence CellRef is accepted. The only workaround is to list all summands in `cells`. That highlights every summand as affected and puts them all into the fingerprint, so adding or removing one item in a section changes the fingerprint and the review decision is lost (verified). Each detector author will choose differently, so 'confirmed only on verified input data' (Part B.1) will hold for some detectors and not others.

**Fix:** Add inputs: Sequence[CellRef] = () to IssueFactory.create. Resolve and validate both inputs and evidence-item cells. Apply the confidence policy to cells plus inputs, and treat inputs whose parse_status is not exact or inferred as unverified. Store the inputs on the issue (ValidationIssue.input_cells or a calculation evidence item). Fingerprint only on detector, category, anchor-cell coordinates and fingerprint_key.

## 6. [high] backend/app/validation/registry/registry.py :: DetectorRegistry.register; backend/app/validation/contracts/issue_factory.py :: IssueFactory.create; backend/app/validation/pipeline.py :: ValidationPipeline._run_step

**Problem:** No code reads DetectorSpec.evidence_classes or issue_categories. Verified: a spec with category=statistical that declares only suspected_anomaly can create a confirmed_rule_violation issue carrying an AnomalyScore, and a statistical spec that declares confirmed_rule_violation registers without error. The pipeline checks only detector_id and run_id. A plugged-in ML or research module can therefore show an outlier in red as a confirmed rule violation, against Part B.1 and the UI colour scheme, and nothing in the core stops it.

**Fix:** In DetectorRegistry.register, reject specs whose category does not allow a declared evidence class. Only deterministic and domain may declare confirmed_rule_violation. Statistical, machine_learning and research are limited to suspected_anomaly, extraction_uncertainty and needs_external_context; semantic to semantic_warning and needs_external_context. In IssueFactory.create, reject an evidence_class not in spec.evidence_classes and a category not in spec.issue_categories. Also reject anomaly_score on confirmed_rule_violation, and calibrated=True unless the spec cites a calibration reference. Add tests.

## 7. [high] backend/app/ingestion/base.py :: RawCell, RawSheet, RawWorkbook, IngestionAdapter; backend/app/ingestion/registry.py :: AdapterRegistry contract; backend/app/models/source.py :: BoundingBox; backend/app/models/dataset.py :: Cell.extraction_confidence; backend/app/models/document.py :: DocumentFormat; docs/architecture/overview.md :: Extension points

**Problem:** Normalization, which is about to be written, sees only RawCell(row, column, text, ...), with no page number, bounding box or confidence; RawSheet has no page or table index. A PDF/OCR adapter therefore cannot pass the provenance that Cell.source.bbox and extraction_confidence expect, and normalization will have to be reopened, contrary to the overview's 'None in normalization/validation'. A multi-page BoQ table has two bad options. As one RawSheet per page, the canonical table is split per page, so subtotals, carry-forwards and grand totals never reconcile across pages. As one merged grid, the per-cell page and bbox are lost. BoundingBox has no page width, height, rotation or DPI, and no page manifest exists, so 'px' boxes cannot be drawn on a rendered page. Table-structure uncertainty (which column a PDF token belongs to) has no representation. A digital-PDF cell must be reported as 1.0, giving confirmed violations on a guessed column assignment, or with an invented number, which the brief forbids. The evidence policy also treats extraction_confidence=None as verified. The registry rule 'exactly one adapter per DocumentFormat' cannot hold pdfplumber plus PaddleOCR (plus optional Tesseract) for PDF, or handle mixed digital and scanned pages. DocumentFormat and the hard-coded allowlist in security.detect_format must be edited for every new adapter.

**Fix:** Extend the raw layer now; the change is additive. Add RawCell.page_number, bbox, confidence and structure_status (categorical exact/inferred/uncertain, like ParseStatus). Add a RawTable that can span pages, with region boxes, and a pages manifest (size, rotation, raster DPI) persisted on Document. Mirror structure_status on Cell, and have the evidence policy treat uncertain structure, and missing confidence on PDF/OCR sources, as unverified. Let AdapterRegistry choose by format plus an adapter probe and priority, with per-page fallback, and move extension and magic-byte rules into each adapter's declaration. Correct the overview table.

## 8. [medium] backend/app/models/dataset.py :: Table.column_for_field, Table, Row.cells, ColumnMapping.field_id

**Problem:** Nothing enforces one column per semantic field: column_for_field builds a dict, so the last column silently wins. boq.yaml lists both 'kurztext' and 'langtext' as synonyms of one field (also 'pos'/'oz'/'nr' and 'gp'/'betrag'/'summe'), and German LV exports usually have both Kurztext and Langtext columns. Verified: a table with both mapped to description resolves description to Langtext with no warning. That changes the input to row classification, the duplicate keys and the required-value checks; an empty Langtext would flag every item as missing a description. Manual mapping in Phase 2 can create the same state. Two more invariants are not enforced. 'Every column of the table has an entry' in Row.cells: a sparse row is accepted, IssueFactory.cell_ref then raises NotFoundError, and the whole detector is reported failed, which OCR tables will hit. And mapping.field_id must exist in the profile: any string is accepted.

**Fix:** Add Table validators: a unique mapping.field_id per table, or an explicit primary/secondary flag with documented semantics plus a duplicate_field_mapping ExtractionWarning from normalization; and exactly one Cell per column in every row, with normalization filling empty cells. Check mapping field ids against the profile when a dataset is normalized or validated.

## 9. [medium] backend/app/validation/registry/discovery.py :: discover_detector_classes; backend/app/validation/pipeline.py :: optional-dependency guarantee; backend/app/validation/contracts/detector.py :: DetectorSpec.dependencies

**Problem:** Discovery imports every public module without catching errors per module. Simulated: a statistical module with a top-level `from sklearn.ensemble import IsolationForest` makes discover_detector_classes raise a raw ModuleNotFoundError (not a RegistryError). The app, and test_builtin_packages_discover_without_errors, then fail on any machine without the optional package. The pipeline promises that detectors with missing optional dependencies are 'skipped with reasons', but that only works if authors import lazily inside validate(), which is not documented anywhere. The brief makes statistical, ML and research modules optional.

**Fix:** Catch ImportError per module in discovery and record an 'unavailable' entry (module, missing package), shown in the catalogue and /health. Keep such detectors out of planners and have PlanValidator report them. Document the lazy-import rule in the detector contract, and add a test with a module whose import fails.

## 10. [medium] backend/app/validation/contracts/context.py :: ValidationContext.cell, number_value, number, text; backend/app/validation/contracts/detector.py :: Detector.applicability, required_fields; backend/app/models/plan.py :: PlanStep

**Problem:** The accessors that abstain on unusable cells work only through mapped semantic field ids. An undisclosed challenge starts from the generic profile (fields: []), where every column is unmapped. The planned column-oriented detectors (data types, numeric validity, exact duplicates, formula errors, extraction uncertainty) and every statistical detector must then read row.cells[...] directly and re-implement the parse_status/NumberValue abstention rules. That duplicates logic, and the copies will drift: one reads parsed_value, another accepts ambiguous. Applicability can only be stated as required fields. PlanStep has no scope, so a planner cannot say 'MAD on column Betrag grouped by Einheit in sheet LV 2'. Each detector will invent its own table and column keys, holding random column ids that PlanValidator cannot check and that break on re-normalization.

**Fix:** Add column-level accessors that share the same rules (cell_at/number_at/text_at(table, row, column)) and build the field versions on top of them. Let applicability use column properties (inferred_type, type_profile). Add an optional standard PlanStep.scope {table_ids, fields, columns given by field id or a stable key such as source_column_number}. PlanValidator validates it against the dataset (validate(plan, profile, dataset)), and detectors read it from the context.

## 11. [medium] backend/app/models/profile.py :: DomainProfile.fields, FieldRole.REFERENCE, PROFILE_FIELD_TYPES, RowClassificationRules; backend/app/normalization/builder.py :: classification contract

**Problem:** A profile is one flat field list applied to every table, so a dataset with different kinds of tables cannot be described: BoQ items plus a 'Zusammenstellung' summary sheet, or a challenge with Orders and Customers sheets. The required fields of one table get flagged as missing on the other. The same field (customer_id) cannot be the key in one table and a reference in another. FieldRole.REFERENCE ('points at another row's identifier') cannot name a target table, so cross-table reference integrity cannot be configured. PROFILE_FIELD_TYPES excludes datetime (verified: a datetime field fails validation), so a profile for timestamped data must declare date or text and then misreport types. The normalization contract also does not say whether a row is an item or text when a profile has no item_value_fields. An implementer following RowKind.TEXT ('text-only row') will classify every row of an all-text table as TEXT under the generic profile, and rows() (item rows by default) then checks nothing.

**Fix:** Add optional table_types to DomainProfile, each with its own fields, synonyms, required fields and row-classification overrides, and add Table.table_type, set by normalization and overridable in schema review. Give reference fields a target {table_type, field_id}. Add DATETIME to PROFILE_FIELD_TYPES. State in the normalization contract that, without item_value_fields, every non-blank, non-total row is an item.

## 12. [medium] backend/app/models/run.py :: ValidationRun.plan, DetectorRunReport; backend/app/validation/pipeline.py :: ValidationPipeline.execute; backend/app/validation/planner.py :: Planner; backend/app/core/config.py :: ValidationLimits

**Problem:** Part F needs up to four passes with strict cycle limits, but a run holds one plan. The Planner protocol sees only (dataset, profile), with no earlier findings or reports to 'identify gaps' from. Every limit applies per execute() call: max_plan_steps and the duplicate-step guard reset on each call, and seen_fingerprints is a local variable. An orchestrator calling execute() four times under one run can therefore run 4 x 64 steps, repeat identical steps across passes and store duplicate findings. There is no time or cost budget and no per-detector timeout: spec.cost is never read, and detectors run synchronously in the request thread. There is also no model for the LLM's interpretation or consolidation output grounded in issue ids or cells, and no record of what data the LLM saw or of the user's approval to send it to an external provider. The overview's 'LLM planner: no core changes' cannot hold.

**Fix:** Add ValidationRun.passes: list[RunPass{index, purpose, plan, reports, planner_input_digest}] and DetectorRunReport.pass_index. Add a run-scoped ExecutionBudget owned by the run: max_passes, max_total_steps, max_cost (spec.cost x rows), max_seconds and a per-detector deadline checked through the context. Enforce it across execute() calls, together with run-wide sets of steps and fingerprints. Extend Planner to plan(dataset, profile, history). Add a RunAnalysis model whose claims must cite existing issue ids or cell refs (validated), plus audit actions for planner input and external-provider approval.

## 13. [medium] backend/app/repositories/base.py :: DatasetRepository, ValidationRunRepository.latest_for_dataset, IssueQuery; docs/api/rest-api.md :: dataset/rows/summary endpoints

**Problem:** DatasetRepository can only add and get whole revision snapshots. Measured with the test builder: a 5,000-row x 8-column table is a 20.8 MB JSON snapshot that takes 1.7 s to load. The documented rows endpoint (offset/limit) has to load that for every grid page, and every one-cell correction writes another full snapshot. Reads ignore the revision: latest_for_dataset(dataset_id) and IssueQuery take no revision, and neither do the REST dataset, rows and summary endpoints. After a correction creates revision 2, the grid shows revision-2 values with revision-1 findings. IssueQuery's table_id/row_id match only an issue's primary location. Findings that span rows are therefore missing from the partner row's results and from the other sheet's results: exact or near duplicates, semantic clusters, and cross-sheet summary reconciliation, where table_id defaults to cells[0]. There is no lookup by fingerprint for carrying review decisions over.

**Fix:** Store tables and rows as rows keyed by (dataset_id, revision, table_id, row_id), with copy-on-write revisions: unchanged rows are shared and overrides are stored separately. Add get_structure(dataset_id, revision) and rows(dataset_id, revision, table_id, offset, limit). Add dataset_revision to IssueQuery, make the latest-run lookup revision-aware, and put the revision in API paths. Store affected cells in an issue_cells index so table_id/row_id filters match any affected cell, and add a query by fingerprint.

## 14. [medium] backend/app/validation/contracts/context.py :: ValidationContext; backend/app/validation/contracts/detector.py :: Detector.validate ('must not ... perform I/O'), DetectorSpec; backend/app/validation/pipeline.py :: _run_step (detector() takes no arguments)

**Problem:** The context holds exactly one dataset plus the profile, units and currencies. Detectors are instantiated with no arguments, and the contract forbids I/O. The brief's optional local embeddings, research algorithms with pre-trained weights, and optional external reference datasets (price catalogues, code lists, a second uploaded document) have no supported way in. The first such detector will either open files itself (any path, a hidden dependency) or force a change to ValidationContext and the pipeline. A finding also cannot reference a cell in a reference document: CellRef has no dataset or document id, and IssueFactory resolves refs only against the run's dataset. DetectorSpec (extra='forbid') lacks the Part G metadata: assumptions, minimum samples, preprocessing, compute needs beyond low/medium/high, randomness and seed, output interpretation, baseline comparison. A research module cannot describe itself to the planner without a core change.

**Fix:** Add context.resources: a read-only provider of registered reference tables and model artifacts by id, from configured directories only and with no network access. Detectors declare them in DetectorSpec.required_resources, and applicability checks them. Allow reference datasets in the context, with CellRefs that carry dataset_id/document_id. Add the optional Part G fields to DetectorSpec now, or a typed research_metadata sub-model.

## 15. [low] backend/app/validation/pipeline.py :: ValidationPipeline.execute; backend/app/models/run.py :: ValidationRun.profile_id; backend/app/profiles/loader.py :: ProfileCatalog

**Problem:** The pipeline never compares dataset.profile_id/profile_version with the profile it receives. Runs record only profile_id, and the catalogue holds one version per id. The YAML profile for an undisclosed challenge will be edited repeatedly, so datasets normalized under v1 (mapped to since-renamed fields, with old constraints) get validated against v2 without warning. Two runs on the same revision can then differ with no record of why, because field constraints, required flags, unit aliases and row patterns are not part of DetectorRunReport.config.

**Fix:** Have the pipeline reject, or warn on, a profile id or version mismatch. Store profile_version and a content hash on ValidationRun. Keep a profile snapshot per version (a catalogue keyed by (id, version), or a copy persisted with the dataset), or force re-normalization when the version changes.
